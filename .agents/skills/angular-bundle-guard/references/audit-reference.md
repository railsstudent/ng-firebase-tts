# Bundle Guard Reference: Script Terminology & Audit Vectors

Consult this reference during **Step 3** when interpreting the output of `analyze-bundle.mjs`, diagnosing initial bundle leaks, or optimizing lazy chunks and component CSS.

## 1. Script Output Terminology (`analyze-bundle.mjs`)

### Output Chunks Section

- **`Inputs: <file> (<size>), ...`**: The top 3 source files (by `bytesInOutput` in `stats.json`) compiled into a non-main JS chunk (`chunk-*.js`). Identifies which route, `@defer` block, or vendor package owns that chunk.
- **`Styles: <total> (<pct>% of chunk) [Rules: <size>, Tailwind @property: <size>]`**:
  - **`Styles` total**: Total bytes inside the JS chunk occupied by Angular's `ViewEncapsulation.Emulated` `styles: ["..."]` strings.
  - **`Rules`**: Bytes used by your actual compiled CSS selectors and declarations.
  - **`Tailwind @property`**: Bytes used by Tailwind v4's `@property --tw-*`, `@layer properties { @supports ... }`, and scoped `@keyframes` preamble (~2.5–3.2 kB per component stylesheet whenever `@apply` uses shadow, ring, gradient, transform, or animation utilities).

### Main Bundle Breakdown Section

- **`Top Input Contributors in Main`**: Individual source and `node_modules` files contributing the most bytes to `main-*.js`.
- **`Grouped Package Breakdown in Main`**: Bytes in `main-*.js` aggregated by npm package (`@angular/core`, `@angular/router`, `firebase`, etc.) or app folder (`app/core`, `app/features`, `app/shared`).

### Component CSS & Dead Class Optimization Audit Section

`analyze-bundle.mjs` prints a bounded summary of the **8 Initial Bundle Vectors**, the **3 Lazy Chunk Vectors**, and these **4 CSS categories** to stdout and writes the **exhaustive itemized tables** (with clickable `file://` links, `.selector` names, exact utilities to move to `.html` or keep in `.css`, and `⚠️ Test Queries Selector` badges) to `<tmpdir>/bundle-audit-report-<hash>.html` via `os.tmpdir()`:

- **PostCSS `"base"` Recommendation (Informative Tip, Not an Error/Smell)**:
  - Checks `postcss.config.json` and `.postcssrc.json` across `[projectRoot, workspaceRoot]` (matching Angular CLI's resolution order) for `@tailwindcss/postcss`. If `"base"` is missing, recommends setting `"base"` to the target app's relative source directory (e.g., `"base": "./src"` or `"base": "./projects/my-app/src"` in a monorepo) so Tailwind only scans that app's source files and keeps `styles-*.css` smaller.
- **`1. Dead / Unused CSS Classes`**:
  - For component `.css` files: Any `.class` selector not referenced in sibling runtime `.html` or `.ts` files (excluding `.spec.ts` and excluding global overrides of `src/styles.css`).
  - For global `src/styles.css`: Any `.class` or `@utility <name>` not referenced anywhere across `src/**/*.{html,ts,css}`, plus any unused `@theme` token or any `prefix-(--var)` utility in CSS that should be replaced with a standard `@theme static` utility.
- **`2. Short Static @apply Classes (<= 3 utilities -> Full Move to HTML)`**:
  - Single-class selectors in component `.css` files (and `@utility <name>` rules in `src/styles.css`) whose `@apply` rule contains 1–3 Tailwind utilities (including `@theme static` utilities like `text-primary`, `text-secondary`, `text-muted`), where replacing the class name in `.html` keeps the target HTML element at `<= 3` total classes (`(currentHtmlClassCount - 1) + utilities.length <= 3`), and the class is not dynamically bound (`[class.foo]`, `[class]`, `[ngClass]`), not referenced in `.ts`, not `:host`, and not overriding a global `.class` in `src/styles.css`.
  - **Why inline to HTML**: Global `styles-*.css` already includes common static utilities, so moving them to `class="..."` in `.html` adds `0 B` to global CSS while shrinking the JS chunk (and removing every `@apply` from a component eliminates its ~3 kB `Tailwind @property` block entirely).
  - **Unit Test (`*.spec.ts`) Selector Guardrail**: If `analyze-bundle.mjs` reports `⚠️ TEST WARNING: Queried in <file>.spec.ts:<line>`, unit tests query that class via `By.css('.<cls>')`, `querySelector('.<cls>')`, or `classList.contains('<cls>')`. Always warn the user to either **keep `<cls>` alongside the inlined utilities in `.html`** (e.g., `class="results-wrapper flex flex-col gap-6"` while deleting `.results-wrapper` from `.css`) or **update the `.spec.ts` selector** at the linked line.
  - **Global Override Guardrail (`src/styles.css`)**: Never inline or delete a component `.css` rule whose selector name matches a global class in `src/styles.css` (e.g., `.error-block` in `sign-in-modal.component.css` overriding `mt-6` on global `.error-block` in `src/styles.css`). Replacing the class name in `.html` strips all global styles from `src/styles.css` and breaks unit tests querying `.error-block`, while inlining utilities alongside the global class loses Angular's `[_ngcontent]` specificity override against unlayered rules in `src/styles.css`.
- **`3. Partial Static Splits (Keep class name in HTML + move up to freeHtmlSlots utilities to HTML)`**:
  - Component `.css` rules that cannot be fully moved (`countAfterMove > 3` or shared across multiple selectors in the same `.css` file) where the matching HTML elements still have free class slots (`freeHtmlSlots = 3 - currentHtmlClassCount > 0`, e.g., `2` free slots when `<div class="foo">` has 1 class, or `1` free slot when `<div class="foo bar">` has 2 classes).
  - **Keep the original class name in `.html`** (`class="<selector> <moved-utilities>"`) on **every** matching element in `.html` (check all line numbers and `⚠️ Nx in file` badges reported in `HTML Locations`) and keep the remaining utilities inside `.css`.
  - **`x:*` Variant Pair Guardrail**: When moving classes to `.html`, move or keep matching `x:*` pairs together (e.g., `grid-cols-*` with `md:grid-cols-*`, `border-*` with `focus:border-*`) so unlayered component `.css` styles don't override `@layer utilities` classes in `.html`.
- **`4. Duplicate @apply Rules`**:
  - Catches three forms of duplication: (a) two selectors in the same `.css` file sharing `>= 5` identical `@apply` utilities (`compareTwoRulesInSameFile`), (b) comma-separated multi-selector rules like `.a, .b { @apply ... }` where extra class names can be consolidated into a single class (`checkCommaSeparatedClasses`), and (c) identical remaining `@apply` rules with `>= 4` utilities (`utils.length > 3`) repeated `>= 2` times within or across component `.css` files (`findIdenticalRulesAcrossFiles`) to be consolidated into a single class or a shared `@utility` in `src/styles.css`.

### Leak Detection Audit Section

- **`Non-Baseline Package in Main (<pkg>)`**: Any `node_modules/<pkg>` bundled into `main-*.js` outside the core Angular startup allowlist (`@angular/core`, `@angular/common`, `@angular/platform-browser`, `@angular/router`, `@angular/service-worker`, `rxjs`, `tslib`). Treated as an informative review item: verify if it is genuinely needed on initial startup or can be moved behind `loadComponent`, `@defer`, or `injectAsync`.
- **`Eager Component in Main`**: Any file under `src/app/` containing `@Component(` (excluding the root `app.ts` / `app.component.ts` shell) bundled into `main-*.js`. Verify that only the primary landing (**Home**) component and root shell components are eager, and secondary routes use `loadComponent` or `@defer`.

## 2. The 8 Initial Bundle Vectors

| Vector | Why It Hoists Code into `main.js` or Vendor Chunks | Fix & Trade-Off Check |
| :--- | :--- | :--- |
| **1. Mixed Barrel File (`index.ts`)** | An eager module in `main.js` imports from a barrel (`@/core/<domain>`) that also re-exports a module whose exported symbols are never used by any other file in `main.js` (or is loaded via `injectAsync()`). The bundler evaluates the barrel and pulls the unused module into `main.js`. | Keep lazy-only modules (`injectAsync` targets and modules unused by `main.js`) **out** of barrel `index.ts` files. Import them via direct file path (`@/core/<domain>/foo`). |
| **2. Value Import Instead of Type Import** | `import { HeavyClass } from '...'` used only for a TypeScript type annotation or interface emits a runtime module edge if not elided or if referenced in DI metadata. | Use `import type { HeavyClass } from '...'` or extract a pure `.interface.ts` file. |
| **3. Top-Level Heavy SDK Import** | A static top-level `import { ... } from 'firebase/ai'` (or similar heavy SDK) inside a service that is reachable from an eager component. | Use dynamic `await import('firebase/ai')` inside the async method, or load the service via `injectAsync()` at the UI boundary. |
| **4. Broken or Missing `@defer` Boundary (Below-the-Fold / Modals / Panels)** | A `@defer` component is referenced as a runtime value in the parent class (e.g., `viewChild(DeferredComp)`), imported via a shared barrel `index.ts`, or a non-critical modal/panel/below-the-fold child inside the eager shell/Home component is not wrapped in `@defer`. | Wrap non-initial modals/panels/heavy children in `@defer`; query deferred children by template ref (`viewChild<DeferredComp>('ref')`); use `import type { ClassName }`; and import deferred components directly from `.component.ts`. |
| **5. Redundant Nested `injectAsync()` & Sequential `await import()`** | Service A is already lazy-loaded (via `injectAsync()` or inside a `@defer` component) and calls `injectAsync()` again for small Service B, or an `async` function calls `await import('a')` followed by `await import('b')` sequentially instead of `Promise.all([import('a'), import('b')])`. | Follow the **`injectAsync()` vs. `@defer` rule**:<br>• **Component on the initial page (not `@defer`) + heavy service**: Use `injectAsync()` so the heavy SDK only downloads on user action.<br>• **Component already inside `@defer` (or already-lazy service) + small service**: Use normal `inject()` (`injectAsync()` inside `@defer` is overkill unless the service loads a huge new SDK not already downloaded).<br>• **Multiple `await import()` calls in the same function**: Start pure module imports concurrently with `Promise.all([import('a'), import('b')])` (do not assume arbitrary `await someMethod()` calls are independent). |
| **6. Non-Home Route `component:` or Heavy Route Guard / Resolver** | Using `component: FeatureComp` instead of `loadComponent` on secondary routes in `app.routes.ts`, or attaching a `canActivate` / `resolve` guard that statically imports a heavy service. **Guardrail**: The primary landing / **Home component** should remain **eagerly loaded** (`component: HomeComponent`) to avoid an extra network waterfall hop on first paint! | Keep the default **Home component** eager for fast LCP, use `loadComponent` / `loadChildren` only for secondary routes, and keep route guards lightweight (or lazy-load heavy dependencies inside the guard body). |
| **7. `app.config.ts` Providers & Initializers** | Registering `provideAppInitializer()`, HTTP `withInterceptors([...])`, or a custom `ErrorHandler` in `app.config.ts` that statically `inject()`s a feature service or heavy SDK. Everything reachable from `app.config.ts` is bundled into `main.js`. | Keep `app.config.ts` providers minimal; lazy-load heavy dependencies inside the interceptor/initializer callback via `injectAsync()` or `await import(...)`. |
| **8. Static JSON / Data Assets vs. `resource()` Vendor Overhead** | Static `import data from './destination.json'` in an eager file inlines the JSON payload into `main.js`. **Warning**: replacing it with `resource()` or `httpResource()` can **increase the initial vendor chunk** if Angular's `resource` or `@angular/common/http` runtime wasn't already bundled—and never use a manual `void fetch(...)` into a `signal()` (anti-pattern). | Always compare net **Initial Total (`main.js` + vendor chunks)**:<br>• Use `resource()` / `httpResource()` when the JSON savings outweigh the vendor chunk delta (or when `resource` / `httpResource` is already in the vendor chunk).<br>• If the JSON is smaller than the `resource()` vendor overhead, keep the static JSON import or load it via `resource({ loader: () => import('./destination.json').then(m => m.default) })` inside a lazy/`@defer` boundary. |

## 3. The 4 Lazy Chunk & Component CSS Vectors

| Lazy Vector | Problem | Fix & Best Practice |
| :--- | :--- | :--- |
| **L1. Bloated Lazy Route / `@defer` Chunk** | A lazy component statically imports heavy sub-dialogs, visualization widgets, or SDKs that are only needed on user action (e.g. clicking a secondary tab or modal). | Wrap secondary features inside the lazy view in nested `@defer (on interaction)` blocks or load them via `injectAsync()` on click. |
| **L2. Sequential Lazy Chunk Waterfall** | Chaining multiple one-by-one dynamic loads (Lazy/`@defer` Component -> `injectAsync(ServiceA)` -> `injectAsync(ServiceB)` or sequential `await import('a'); await import('b')`) forces the browser to download files one after another before the user gets a response. | • If the component is already inside `@defer` and the services are small, replace `injectAsync()` with normal `inject()` so they bundle together in the `@defer` chunk.<br>• If two `injectAsync()` services or multiple `await import()` calls must stay lazy, start them together with `Promise.all([import('a'), import('b')])` instead of awaiting them one after another (only parallelize `await import()` or `injectAsync()`, as arbitrary `await method()` calls may have stateful dependencies). |
| **L3. Shared Lazy Vendor Chunk Leaks** | Two separate lazy features import different helpers from a shared barrel or utility file, causing esbuild to generate an unnecessary shared lazy `chunk-*.js` loaded by both routes. | Avoid barrel files in feature and shared directories; import directly from discrete `.service.ts` or `.util.ts` files to keep lazy chunks decoupled. |
| **L4. Component CSS Bloat & Dead CSS Classes in JS Chunks** | Angular `ViewEncapsulation.Emulated` compiles component `.css` files (including dead/unused classes left behind after refactoring) into `styles: [...]` strings inside the JS chunk, and Tailwind v4 appends ~3 kB of `@property --tw-*` / `@supports` definitions per component stylesheet. Wrapping `<= 3` static utilities in custom `.css` classes duplicates rules in the JS bundle instead of reusing global `styles.css` utilities. | • **Delete dead CSS classes & unused/non-`@theme` `--*` tokens**: Remove any `.class` in a component `.css` file not referenced in its sibling runtime `.html` or `.ts` files, any dead `.class` / `@utility` / `@theme` token in `src/styles.css` unused across `src/`, and migrate any `prefix-(--var)` in CSS into `@theme static` in `src/styles.css`.<br>• **Migrate short static classes (`<= 3` total HTML classes after full move)** from `.css` (or `@utility` in `src/styles.css`) to inline HTML `class="..."` attributes, and report the estimated byte savings in the JS chunk.<br>• **Enforce `<= 3` total HTML classes after move (`countAfterMove <= 3`)**: Always count existing classes in the target element's HTML `class="..."` attribute (`currentHtmlClassCount`). Full moves require `(currentHtmlClassCount - 1) + utilities.length <= 3`; partial splits (which keep `.class` in HTML) require `currentHtmlClassCount + movedUtilities.length <= 3`. When a component rule has more utilities than fit in a full move (`countAfterMove > 3`) and the HTML element still has free slots (`freeHtmlSlots = 3 - currentHtmlClassCount > 0`), surface it under **3. Partial Static Splits** as an engineer-choice split (`Keep <class> + add (engineer choice: any N utilities)`), with the note: *"When moving classes to `.html`, move or keep matching `x:*` pairs together (e.g., `grid-cols-*` with `md:grid-cols-*`, `border-*` with `focus:border-*`) so `.css` styles don't override `.html` classes."*<br>• **Skip Tailwind `list-*` utilities, dynamically bound classes (`[class.foo]` / `[class]` / `[ngClass]`), & `.ts`-referenced classes**: Never inline or split rules containing Tailwind list utilities (`list-disc`, `list-decimal`, `list-none`, `list-(...)`, `list-[...]`, `list-inside`, `list-outside`, `list-image-*`), dynamically bound classes in `.html`, or classes referenced in `.ts` files.<br>• **Guard unit test selectors (`*.spec.ts`)**: If a class is queried in `*.spec.ts` (`By.css`, `querySelector`, `classList`), warn the developer to either retain the class name in `.html` alongside the inlined utilities or update the `.spec.ts` selector.<br>• **Never inline global overrides (`src/styles.css`)**: Keep component `.css` rules that override a global `.class` in `src/styles.css` (e.g., `.error-block`) in `.css`.<br>• **Never convert `:host` to HTML**: Keep `:host` in the `.css` file (or component `styles: [...]`).<br>• **Consolidate duplicate `@apply` rules within or across files**: When two class selectors in the same file share `@apply` utilities (either as separate `.a { ... }` and `.b { ... }` blocks, or as `.a, .b { ... }`), consolidate both HTML elements to use a **single shared class name** (plus any unshared static utilities inline in `.html`) and remove the second class selector from `.css`. When identical `@apply` rules with `>= 4` utilities remain across `>= 2` component `.css` files, extract a shared `@utility` into `src/styles.css` and remove the duplicate component `.css` rules. |
